# Backend v1.0 release readiness

Branch: `fix/backend-v1-release-hardening`, based on `main` at `75c5e56`. Backend/API and AdminJS scope, following the original request. Final application code: `4fbf1ce051a7e835becb129202d962c4ef71ddfb`. No additional service, Redis, schema migration, public GraphQL field change, or feed redesign was introduced.

## Changes

| Finding                                               | Result                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-08: unvalidated post images and EXIF/GPS            | Allowed JPEG/PNG/WebP bytes must match the declared format and exact ticket size, fully decode, and re-encode without metadata. Streams and output are capped at 5 MiB, decoding at 4 million pixels and 5 seconds. The existing shared decoder pool, now limited to two active jobs, also bounds download/publish memory. Invalid/overloaded processing fails without creating a Post; finalization/recovery obligations remain intact. |
| F-09: public photos after owner deletion              | The same database transaction now queues object deletion/CDN purging and removes Post and discussion-image references. It reuses the existing deletion worker. Administrative removal and inactivity expiry retain their established restoration/renewal behavior.                                                                                                                                                                       |
| F-10: carrier/shared-network users share small quotas | A generous 10,000-per-minute shared-IP ceiling runs before authentication; business quotas use verified account IDs afterwards. Anonymous calls retain IP quotas.                                                                                                                                                                                                                                                                        |
| F-15: geographic lookup amplification                 | The operation cost budget limits expensive per-Post vet lookups and aliases. It runs on every operation, including cached documents with changed variables, with a 5,000 cost budget and 2,000 analyzed-node cap. Existing depth limits remain. No new batching/database architecture was added.                                                                                                                                         |
| F-06: nested self phone returns ciphertext            | Relationship loaders decrypt phone fields; existing self-only field guards continue hiding private values from other accounts.                                                                                                                                                                                                                                                                                                           |
| F-12: inconsistent mating page validation             | Invalid page sizes now receive the same validation behavior as other post feeds.                                                                                                                                                                                                                                                                                                                                                         |
| F-17: ignored asynchronous cache failures             | Cache write/cleanup promises now handle rejections without replacing mutation results/errors.                                                                                                                                                                                                                                                                                                                                            |
| Additional: duplicate simultaneous retries            | A reproduced get/set race is now prevented by a synchronous, process-local reservation that is released on completion/error. This follows the existing single-replica architecture.                                                                                                                                                                                                                                                      |
| Additional: oversized retry keys                      | A probe accepted and cached a 12,000-character retry key. Mutation retry keys now must be a single string of at most 128 characters before cache allocation. Tests reject oversized/multiple keys and accept the exact boundary.                                                                                                                                                                                                         |
| Additional: cache memory growth                       | The installed cache-manager ignores the old `max` option. A supported Keyv LRU memory adapter now enforces the intended shared 50,000-entry limit. Real Nest cache tests verify recency-based eviction and millisecond TTLs. No external cache was added.                                                                                                                                                                                |
| Additional: ambiguous storage write                   | When storage accepts sanitized bytes but its response is lost, the failed ticket retains the final object key. Existing durable cleanup can reclaim both staging and final objects; a database-backed regression exercises that failure.                                                                                                                                                                                                 |
| Additional: production configuration                  | Production rejects Firebase Auth emulator configuration, and startup validates actual AES-256 key bytes. Admin geocoding correctly honors `false`/`off` flags.                                                                                                                                                                                                                                                                           |
| Dependencies / CI                                     | Decoder, GraphQL utilities, HTTP parsing, proxy, gRPC, protobuf, Axios/ProseMirror and brace-expansion patches applied without upgrading the NestJS or AdminJS major versions. CI now rejects high/critical runtime advisories for both services.                                                                                                                                                                                        |

Each change is committed on the new branch. The formerly expected-failing upload/deletion assertions are ordinary tests now; new database-backed regressions cover their behavior in the existing release-gated integration suite.

## Deployment evidence required before real users

1. Apply migrations through `0063` using the API-owned pre-deploy command `node dist/database/migrate.js`. Verify `posts.coordinates` is `geometry(Point,4326)` and the `listed_at` indexes exist. Plan a lock window if an existing database needs the SRID rewrite. Follow ADR 0007's coordinated contraction only when upgrading an old deployment that still queries `saved_searches`.
2. Set actual production Firebase/R2 credentials and `NODE_ENV=production`; keep the Auth emulator unset and preserve the stable, valid `PHONE_ENCRYPTION_KEY` across deployments and restores. Configure separate AdminJS cookie/session secrets and administrator credentials using the [deployment guide](deployment/three-service-railway-release.md). Configure the paired `TERMS_URL`/`TERMS_VERSION` if the published Terms gate is intended to be enabled. Confirm the deployed proxy overwrites forwarded headers for the configured one trusted hop.
3. Provision `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_API_TOKEN` with cache-purge access for the actual media domain. Exercise owner deletion against real R2/CDN and verify the public URLs stop serving photos and queued work reaches `COMPLETED`. Missing purge credentials produce visible retries/failures; a source test cannot prove actual CDN invalidation.
4. Prevent unauthenticated public access to `/staging/` on every media delivery hostname, and disable the bucket's public `r2.dev` development endpoint in production so it cannot bypass custom-domain access controls. Presigned uploads and backend reads use the authenticated S3 endpoint. Verify a raw staged upload cannot be downloaded publicly while its eventual sanitized Post image can. Cloudflare documents custom-domain access controls and warns that `r2.dev` access independently bypasses them: [Public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/).
5. If old media is carried into the first production dataset, sanitize/reprocess and purge those existing originals; the new upload path protects new publications. Also review older owner-removal records for media retained under the old behavior; `REMOVED` status alone does not distinguish owner deletion from administrator removal. Preserve the administrator retention policy when reconciling those records. A fresh dataset has no legacy-media backfill requirement.
6. Smoke-test the real FCM/APNs provider and physical-device receipt, including an ordinary notification and suppression after opt-out/Block/sign-out. The durable worker's retry/isolation tests do not prove external credentials or delivery. Preserve the single API replica; process-local rate/idempotency state remains intentional and is not restart-persistent/exactly-once.
7. Perform staging traffic/capacity checks with the intended infrastructure and use the existing manual capacity-review checkpoint. Watch RSS, latency and push/media-deletion queue age. The gate's functional/query-plan tests do not certify throughput for an unspecified number of concurrent real users.
8. Confirm scheduled database backups and demonstrate a restore to an isolated target; record the deployed health checks, alerting and resource limits from the existing [launch runbook](deployment/hobby-launch-runbook.md). Repository settings alone do not prove those operational controls are active.

These platform settings were not deployed or externally verified in this change.

## Items intentionally outside the backend fixes

- F-03's new content-edit features and F-13's rescue/adoption contact-policy choice require product decisions; existing supported workflows were preserved.
- F-16's feed redesign was not undertaken. Existing spatial/feed indexes and query-plan tests remain; further changes should follow measured staging bottlenecks.
- The accepted single-instance cache/ban-propagation policy and Windows/PG18 test-portability notes do not require a launch architecture rewrite.
- A source check still finds Android release signing assigned to the debug key in `frontend/android/app/build.gradle.kts:41`. Store release signing and the earlier audit's mobile/device/store evidence are separate app/platform work. Backend verification does not certify the entire mobile release.
