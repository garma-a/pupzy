# Post Lifecycle Transition & Side-Effect Contract

This document is the authoritative contract for every Post lifecycle status change made by the NestJS GraphQL API and the AdminJS service. The machine-readable half of the contract lives in `src/common/contracts/post-lifecycle.contract.ts`, which both services import, so the transition rules and lock namespace cannot drift between them.

This document covers the shared lifecycle statuses. Earlier slices were preparatory; owner closure (ticket 03) adds MATING and FOUND_STRAY outcomes and terminates pending direct interactions when a listing closes. Ticket 12 adds `EXPIRED` plus explicit owner renewal, and ticket 13 extends that window to ADOPTION. Ticket 08 adds administrator resolution (`ADMIN_RESOLVE`) and ticket 09 adds administrator reopening (`ADMIN_REOPEN`). Ticket 06 adds `ANIMAL_DECEASED`, the RESCUE-only closure outcome recorded when the animal died. Inactivity expiry has its own authoritative contract: `post-expiry-and-renewal-contract.md`. Administrative resolution and reopening have their own staff contract: `admin-case-resolution-contract.md`.

---

## 1. Actors and entry points

| Transition      | Actor                                 | Entry point                                  | Allowed type/status                                  |
| --------------- | ------------------------------------- | -------------------------------------------- | ---------------------------------------------------- |
| `OWNER_CLOSE`   | Post owner                            | GraphQL `updatePostStatus`                   | `ACTIVE` → a completed outcome of the Post's type    |
| `OWNER_REMOVE`  | Post owner                            | GraphQL `deletePost`                         | any non-Removed status → `REMOVED`                   |
| `OWNER_RENEW`   | Post owner                            | GraphQL `renewPost`                          | `ACTIVE`/`EXPIRED` → `ACTIVE` under the type policy  |
| `EXPIRE`        | System job (`PostExpiryProcessor`)    | shared inactivity boundary                   | `ACTIVE` → `EXPIRED` under the type policy           |
| `ADMIN_RESOLVE` | Administrator (`ADMIN`/`SUPER_ADMIN`) | AdminJS type-specific resolution actions     | `ACTIVE` → a completed outcome of the Post's type    |
| `ADMIN_REOPEN`  | Administrator (`ADMIN`/`SUPER_ADMIN`) | AdminJS `reopenPost`                         | a completed outcome → `ACTIVE`                       |
| `ADMIN_REMOVE`  | Administrator (`ADMIN`/`SUPER_ADMIN`) | AdminJS `removePost`, ban Post cascade       | `ACTIVE` → `REMOVED`                                 |
| `ADMIN_RESTORE` | Administrator (`ADMIN`/`SUPER_ADMIN`) | AdminJS `restorePost`                        | `REMOVED` → `ACTIVE`                                 |

Owner closure targets (`OWNER_CLOSURE_TRANSITIONS` and, for LOST Posts, `LOST_SUBTYPE_CLOSURE_TRANSITIONS` in the contract):

| Post type  | Direction (`report_type`) | Owner closure outcomes                |
| ---------- | ------------------------- | ------------------------------------- |
| `RESCUE`   | —                         | `RESOLVED`, `ANIMAL_DECEASED`         |
| `LOST`     | `LOST_PET`                | `REUNITED`                            |
| `LOST`     | `FOUND_STRAY`             | `RESOLVED`, `REUNITED`                |
| `ADOPTION` | —                         | `ADOPTED`                             |
| `PRODUCT`  | —                         | `SOLD`                                |
| `MATING`   | —                         | `RESOLVED`                            |

`ANIMAL_DECEASED` closes a rescue because the animal died. It is a completed outcome but **not a success**: only RESCUE permits it, and its notifications, corrections and labels never describe it as Rescued (see the glossary definition of **Animal deceased** in `CONTEXT.md`). Every other type rejects it with a `VALIDATION_ERROR`, and it is offered without any evidence gate exactly like `RESOLVED` — the owner or administrator may record either outcome at any time while the rescue is `ACTIVE`.

A Post owner can close only their own `ACTIVE` Post and only into an outcome that belongs to its type (and, for LOST, its direction); every other target returns a `VALIDATION_ERROR`. FOUND_STRAY retains `REUNITED` so existing clients that already send it keep working. A Post already in a completed outcome returns the same invalid-transition error. A non-owner receives `FORBIDDEN`, and a missing or Removed Post resolves to `NOT_FOUND`.

Administrative removal applies only to `ACTIVE` Posts. It can never overwrite a recorded outcome; an administrator who needs to take down a closed Post uses the audited reopening correction first and then removes the active Post, so every step remains explicit and recorded.

Administrative reopening is the correction path for a mistaken Post Resolution. It accepts exactly the completed outcomes (`RESOLVED`, `REUNITED`, `ADOPTED`, `SOLD`, `ANIMAL_DECEASED`) and returns the Post to `ACTIVE`; `ACTIVE`, `REMOVED`, `EXPIRED` and unknown states are rejected. It is administrator-only — owners gain no reopening operation, and `updatePostStatus`, `deletePost` and `renewPost` are unchanged. A Post whose owner is banned is not reopened: the owner row is read under a share lock inside the action transaction, so a concurrent ban settles in one order and a banned account never regains active content through this correction. `REMOVED` Posts are still returned only by `ADMIN_RESTORE`, and `EXPIRED` listings only by explicit owner renewal.

## 2. Status meaning stays distinct

`RESOLVED`, `REUNITED`, `ADOPTED`, `SOLD` and `ANIMAL_DECEASED` are **Post Resolutions** decided by the owner (or by an administrator). Four of them record a successful outcome; `ANIMAL_DECEASED` is the fifth and deliberately non-successful one, so that death is never silently folded into `RESOLVED`/Rescued. `REMOVED` is the administrative/owner takedown soft delete: a moderation action carries a reason, audit row and owner notification. `EXPIRED` is the inactivity state of a renewable listing: it leaves active discovery but keeps direct detail, owner history, media and discussion, is **not** a resolution and does **not** reuse `REMOVED`.

Completed outcomes, owner removal, administrative takedown and inactivity expiry are distinguishable by the stored status, who performed the change, the recorded reason/audit metadata, and the resulting `moderation_status`. See `post-expiry-and-renewal-contract.md` for the full expiry/renewal contract.

## 3. Transaction, locking and side effects

Every transition runs inside one database transaction and takes the shared locks in this order:

1. the transaction-scoped advisory key `comment_discussion:<postId>` (`POST_DISCUSSION_LOCK_NAMESPACE`), then
2. the canonical `posts` row with `SELECT ... FOR UPDATE`.

The Post row is re-read and revalidated after both locks. This is the same order used by Comment discussion mutations, so a competing Comment write, owner transition, administrator action, ban cascade or Block cannot interleave or deadlock. Both services keep their existing retry policy around this boundary (`withDbRetry` on the API side, `runModerationAction` on the admin side).

The status write commits together with its database-side effects; cache invalidation and other external effects run only after commit.

| Side effect                                      | `OWNER_CLOSE`                              | `OWNER_REMOVE` | `OWNER_RENEW`  | `EXPIRE`                                   | `ADMIN_RESOLVE`                            | `ADMIN_REOPEN`                        | `ADMIN_REMOVE`          | `ADMIN_RESTORE` |
| ------------------------------------------------ | ------------------------------------------ | -------------- | -------------- | ------------------------------------------ | ------------------------------------------ | ------------------------------------- | ----------------------- | --------------- |
| `trg_sync_user_post_counts` delta                | none                                       | decrement      | none           | none                                       | none                                       | none                                  | decrement               | increment       |
| Pending Contact Requests / Adoption Applications | terminated (`REJECTED`, records preserved) | unchanged      | unchanged      | terminated (`REJECTED`, records preserved) | terminated (`REJECTED`, records preserved) | unchanged (closed stay closed)        | unchanged               | unchanged       |
| API `user_resolve` cache invalidated             | yes                                        | yes            | yes            | no                                         | no                                         | no                                    | no                      | no              |
| AdminJS dashboard cache invalidated              | no                                         | no             | no             | no                                         | yes                                        | yes                                   | yes                     | yes             |
| `moderation_actions` audit row                   | no                                         | no             | no             | no                                         | yes (`POST_RESOLVED`, internal reason)     | yes (`POST_REOPENED`, internal reason) | yes                     | yes             |
| Owner notification                               | none                                       | none           | none           | none (pre-expiry reminder already sent)    | `POST_RESOLVED_BY_ADMIN` (localized)       | `POST_REOPENED_BY_ADMIN` (localized)  | `POST_REMOVED_BY_ADMIN` | none            |
| Participant completion event                     | captured for every completed outcome       | none           | none           | none                                       | captured for every completed outcome       | superseded + corrected                | none                    | none            |
| Open Post Reports closed                         | no                                         | no             | no             | no                                         | no                                         | no                                    | yes                     | yes             |
| Moderation fields (`moderation_*`)               | unchanged                                  | unchanged      | unchanged      | unchanged                                  | unchanged                                  | unchanged                             | updated                 | updated         |
| Media, discussion and engagement rows            | retained                                   | retained       | retained       | retained                                   | retained                                   | retained                              | retained                | unchanged       |

Notes:

- Closing a listing (`OWNER_CLOSE`, a completed outcome) moves every still-PENDING Contact Request and Adoption Application targeting that Post to the established terminal `REJECTED` state with `responded_at` set, inside the same transaction as the status write. Rows are preserved, never deleted, and the existing uniqueness rules still prevent the participant from re-applying to the same Post. `ADMIN_RESOLVE` performs the same cleanup from the admin boundary.
- Every completed outcome (`RESOLVED`, `REUNITED`, `ADOPTED`, `SOLD`, `ANIMAL_DECEASED`) also captures a durable participant completion event in the same transaction: `POST_COMPLETED` for every non-RESCUE type and `RESCUE_COMPLETED` for RESCUE. The audience is the closure-time snapshot of Boost/save, active Comment/Reply, Contact Request and Adoption Application participation (every application status), deduplicated, excluding the Post creator and the closing actor; delivery rechecks Blocks against both the creator and the closing actor. `ADMIN_REOPEN` supersedes a still-pending event and sends the localized `POST_REOPENED`/`RESCUE_REOPENED` correction to already-delivered participants. Owner removal, administrator removal and inactivity expiry capture no completion event. `RESCUE_COMPLETED` copy is outcome-specific: `RESOLVED` renders the successful-rescue copy while `ANIMAL_DECEASED` renders the distinct "closed (animal deceased)" copy in both languages, so death is never labelled a successful rescue. The localized copy and `related_post_id` routing are specified in `notification-language-flutter-integration-contract.md`.
- `ADMIN_RESOLVE` records a type-specific completed outcome for an `ACTIVE` Post, writes the append-only audit row with the actor, internal reason and outcome, inserts the localized `POST_RESOLVED_BY_ADMIN` owner notification and terminates pending interactions in the same transaction. It leaves `moderation_*` fields and open Post Reports untouched and does not change the owner's counters: a Post Resolution is neither a moderation takedown nor a counter event. See `admin-case-resolution-contract.md`.
- Previously **approved** Contact Requests and Adoption Applications are never touched by a closure. Their existing account-availability, visibility and Block restrictions continue to apply, and the approved participant can still retrieve the owner's WhatsApp link for a Post that is no longer Active (the link is only lost when the Post is Removed).
- Owner removal keeps its established behavior: it does not terminate pending interactions, and approved disclosure is denied because the Post is Removed. Administrative removal, restoration, Account Deletion and bans also keep their existing (stronger) access and cleanup behavior; the contract records them as not terminating pending interactions in this slice.
- The counter delta is applied by the existing `trg_sync_user_post_counts` database trigger, not by application code. A closure from `ACTIVE` to a completed outcome does not change the owner's counters; removal decrements them and restoration restores them.
- Administrative removal records the actor and reason, closes every still-open Post Report in the same transaction, and inserts the owner notification. Restoration preserves the prior `moderation_status` (Clean, Flagged or Pending auto review).
- Administrative resolution never overwrites a recorded outcome: it is offered only while the Post is `ACTIVE`. Correcting a completed outcome is the explicit `ADMIN_REOPEN` transition, which never bypasses removal, moderation, bans or the restoration/renewal paths.
- `ADMIN_REOPEN` returns a completed Post to `ACTIVE` and writes the append-only audit row with the actor, internal reason and corrected outcome plus the localized `POST_REOPENED_BY_ADMIN` owner notification in the same transaction. It leaves `moderation_*` fields, open Post Reports and every interaction row untouched: previously closed Contact Requests and Adoption Applications stay closed, approved access keeps its existing restrictions, and the owner's counters are unchanged. A Post owned by a banned account is rejected, so reopening cannot revive content for a banned account.
- Removal is not destructive: Post media rows, discussion Comments, and upvote/save relationships are retained. Restoration makes them reachable again. Media finalization, deletion and compensation keep their existing durable Staged Upload behavior and are untouched by this contract.
- Expiry is not destructive either: `EXPIRED` retains media, discussion and engagement, stays directly readable, and is left only by `OWNER_RENEW`. Renewal never revives interactions that expiry terminated, and it is rate-limited by the stored `renewed_at` cooldown under the same locks.
- Owner actions never write moderation audit rows or owner notifications; the API invalidates the owner's cached profile after the transaction commits so the refreshed Post counters are served.
- New direct interactions cannot be created after a closure: the creation transaction re-reads the Post under a share lock, so a request or application racing an owner closure settles in exactly one serial order and never leaves a PENDING row on a closed listing. An approval racing a closure likewise settles in one order: approved-before-closure is retained, and a closure that wins leaves the row REJECTED and the approval fails with the established conflict error.

## 4. Isolation and access behavior

The contract preserves the established directional Block isolation:

- A lifecycle transition never crosses account-pair isolation checks, because it only ever changes the state of an existing Post.
- A viewer isolated from a Post's creator (in either Block direction) continues to see the ordinary neutral `NOT_FOUND` for that Post and its type-specific detail queries — both before and after a lifecycle change.
- Administrators retain their moderation visibility and may remove or restore a Post regardless of personal Blocks.
- Owner actions remain owner-only; isolation never grants a third party lifecycle authority.

## 5. What this contract deliberately does not do

The following remain for the tickets that depend on this boundary and must extend the contract rather than duplicate it:

- The RESCUE/LOST 60-day inactivity reminder (ticket 14). Ticket 12 shipped the shared machinery with those policy entries disabled and ticket 13 enabled the ADOPTION 30/27-day window; ticket 14 only enables its policy data and adds tests.
- Termination of pending interactions on owner removal, Account Deletion or bans: those paths keep their existing (stronger) access and cleanup behavior.

## 6. Status consumers and additive rollout

Ticket 06 audited every backend and AdminJS consumer of the Post status values. The table records how each consumer treats `ANIMAL_DECEASED`; consumers that enumerate outcomes derive from `COMPLETED_POST_OUTCOMES` and needed no code change beyond the contract.

| Consumer                                                                   | Handling of `ANIMAL_DECEASED`                                                                                                                        |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `post-lifecycle.contract.ts` (`OWNER_CLOSURE_TRANSITIONS`, `COMPLETED_POST_OUTCOMES`) | Source of truth: RESCUE-only owner/admin closure, reopenable, removable like every non-Removed outcome.                                     |
| Postgres `post_status` enum (migration `0058`)                             | Additive value appended last; no trigger, constraint, view or function enumerates completed statuses, so no further DDL is required.                |
| GraphQL `PostStatus` (both SDL files and generated `src/graphql.ts`)       | Additive enum value with a documented non-success meaning. Old clients that do not know it receive it only for a rescue they are already entitled to read, and must treat unknown values defensively. |
| `updatePostStatus` input allowlist and `PostsService`/`PostsRepository`    | Transport allowlist includes the value; the shared contract enforces RESCUE-only, ACTIVE-only and no evidence gate.                                   |
| Feed/discovery queries (`findHelpFeed`, `findAdoptFeed`, `findMarketFeed`, home feed) | Filter on `status = 'ACTIVE'`, so the outcome leaves discovery automatically.                                                              |
| Owner history (`myPosts`) and direct Post/detail queries                    | Filter on `status <> 'REMOVED'`, so the closed rescue stays readable in owner history with its media and discussion.                                   |
| Post expiry and ban-cascade processors                                      | Filter on `status = 'ACTIVE'`; a deceased rescue is never expired or cascaded.                                                                        |
| `trg_sync_user_post_counts`                                                 | Counts every non-Removed status; the owner's counters are unchanged by the closure.                                                                    |
| Owner/admin completion capture (`posts.repository.ts`, `helpers.js`)        | Capture is gated on `COMPLETED_POST_OUTCOMES`, so the event is captured with outcome `ANIMAL_DECEASED` and no RESCUE/RESOLVED-specific gate.           |
| Notification templates (`RESCUE_COMPLETED`)                                 | `ANIMAL_DECEASED` renders the distinct deceased copy; the successful-rescue copy is only reachable for `RESOLVED`.                                     |
| AdminJS status enum, resource property and `POST_STATUS_LABELS`             | Include the value; the review workspace renders "Animal deceased" and the action history reads "Post marked animal deceased".                          |
| AdminJS resolution actions                                                  | `markAnimalDeceased` is offered only for an `ACTIVE` RESCUE and revalidated under the row lock via `canAdminResolve`.                                  |
| AdminJS queue predicates (`work-queues.js`, `queue-filters.js`)             | Derive from `COMPLETED_POST_OUTCOMES`; the Completed queue includes the value automatically.                                                           |
| Comment eligibility (`comments.service.ts`)                                  | The Post must exist and not be `REMOVED`: text Comments remain allowed on a deceased rescue, and its media and discussion stay readable. Image Comments keep the existing RESCUE/LOST-only rule, which a RESCUE outcome satisfies. |
| New contact-request / adoption-application creation (`contacts.service.ts`, `adoptions.service.ts`) | Reject any Post that is not `status = 'ACTIVE'`, so a deceased rescue accepts no new interactions; earlier approved access keeps its existing availability rules. |
| Push-notification allowlist (`push-delivery.constants.ts`)                  | No new `NotificationType` is involved: `RESCUE_COMPLETED`/`RESCUE_REOPENED` are already allowlisted, so inbox and push delivery use the stored outcome-specific copy. |
| `post-expiry-and-renewal-contract.md`                                       | Expiry/renewal is unaffected: a completed outcome is never renewable and never expires.                                                                |

### Additive rollout compatibility

1. **Storage/API first.** Apply migration `0058_add_animal_deceased_post_status` before deploying API or admin code that writes the value. The migration only appends an enum value, so old code keeps working against the new schema and no existing outcome is reclassified.
2. **API and admin are additive.** No operation, argument, field, nullability or existing enum value changed; `ANIMAL_DECEASED` is a new `PostStatus` value only. Old clients that never send or match it keep working.
3. **Frontend maps the new value.** The Flutter client adds the status to its local enum/labels, renders the deceased copy and routes the notification through `relatedPostId`. Until it does, an old client should ignore or defensively render an unknown enum value rather than treat it as `RESOLVED`/Rescued.
4. **No ordering dependency between services.** The API, the admin service and the completion worker all read the shared contract module, so once both deploy they agree; the durable event stores the outcome string, so a worker that runs after a later deploy still renders the correct copy.
